# Codex修正キュー（第1段階）

管理者が送った修正メモを、このPCのCodexで1件ずつ処理し、修正候補・検査結果・回答を元メモに表示する仕組みです。
**自動commit・push・本番反映は実装していません。** 既存のmainへのpushによるデプロイ設定は変更しません。
現在のmainはpushすると本番反映されるため、この機能の導入と候補の取り込みは別々にレビューしてください。

## 管理画面での操作

1. 管理者としてCODEXメモを開き、「Codexへ送信」を押す。
2. 「Codex修正キュー」で処理待ち・実行中・検査結果を確認する。
3. LEVEL 1は検査成功で「修正・テスト完了（未反映）」。LEVEL 1限定運用ではLEVEL 2・3は候補作成前に「要確認」で止まる。
4. 元メモの結果欄にも回答・ファイル名・テスト結果が表示される。既存の回答と追記は残る。
5. 内容を直して再実行する場合は、追記してから「再実行」を押す。「結果を確認済みにする」はキュー上の確認だけで、元メモを自動で完了にしない。

メモ登録だけでは処理しません。送信確認に表示される通り、送信したメモの本文・履歴・添付画像がCodexに渡ります。
「承認して本番反映」はこの段階では無効です。API経由の承認・反映も拒否します。
停止・保留は処理権限を取り消し、遅れて届いた結果を拒否します。PC側は通常20秒以内の生存確認で停止を検知します。
通信切断・PC終了の場合は再接続時に期限切れを検出し「要確認」にします。同じ依頼を黙って再実行しません。

## 設置と起動

サーバー用の新規6ファイルは `codex_queue.php`、`codex_queue_api.php`、`codex_queue_lib.php`、
`codex_queue_worker.php`、`codex-queue.js`、`codex-queue.css` です。
既存の `codex_memos.php`、`codex_memos_api.php`、`codex-memos.js`、`workspace-ui.js` に連携箇所があります。
これらをレビュー後、既存のGitHub Actionsで導入します。別のFTP・直接転送処理は追加しません。
`.deploy/codex_queue/` 自体は既存の転送除外により本番へ配布されません。

この第1段階ではWindowsのこのPCを使います。常駐サービス・スタートアップ・タスクスケジューラーは登録しません。
処理中はPCとワーカーを起動しておく必要があります。停止中も送信済みメモはキューに残ります。

必要なもの：Git、Python 3.10以降、PHP CLI、Node.js、Playwright、Edge、ログイン済みCodex CLI、既存のSSH鍵・確認済みホスト鍵ファイル。
CodexはChatGPTの保存済みログインを使用できます。APIキーをコードへ書きません。
CLIの非対話実行とJSON出力は[公式の非対話モードの説明](https://learn.chatgpt.com/docs/non-interactive-mode)に基づきます。
今回の実行確認版はCodex CLI `0.154.0-alpha.6.2`です。別バージョンに変える際は、ツール無効化・読み取り専用設定を再検証してください。

1. `config.example.json` を **リポジトリの外** にコピーする（例：`C:/Users/idwor/Documents/Codex/timetable-queue/config.json`）。
2. `codex`、`php`、`node`、`nodeModules` を実在するパスにする。`sshKey`・`knownHosts` は既存の非公開ファイルのパスだけ指定する。鍵の本文を書かない。
3. `rsync` に既存のローカル検証用rsyncのパスを指定する。Linuxでの利用時はインストール済みPlaywright Chromiumを用意し、`browserChannel` を省略する。
4. `repo` は差分・未追跡ファイルのないmainを指定する。設置作業中のリポジトリではワーカーは停止する。
5. `enabled: false` のまま構成確認し、その後 `true` にして1件だけ実行する。

```powershell
# 実際のpython.exeとconfig.jsonのパスを使用
python -B .deploy/codex_queue/worker.py --config C:/Users/idwor/Documents/Codex/timetable-queue/config.json --doctor
python -B .deploy/codex_queue/worker.py --config C:/Users/idwor/Documents/Codex/timetable-queue/config.json --once --memo CM-ここを24桁のメモIDに置換 --max-level 1
```

`--doctor` はローカルの構成確認だけです。SSH接続・サーバー設置・Codexログインの成功までは保証しません。
サーバー側の設置後、まず合成メモ1件で `--once` を確認してから、継続処理を使います。

## LEVEL 1限定運用と相談コードの固定

`--once --max-level 1` は、処理待ちを最大1件取得し、次の順に進みます。

1. 元リポジトリがcleanなmainであることを確認する。
2. キューから1件取得し、依頼全文・追記・画像をCodexへ渡して事前判定する。この段階は読み取りと分類だけ。
3. LEVEL 2・3なら `要確認：LEVEL 1限定運用のため自動処理対象外` として終了する。曖昧な依頼も `needs_clarification: true` を返して終了する。
4. LEVEL 1の場合だけ関連ソースを渡す。ソース確認後に判定が上がった場合、不明点が見つかった場合も停止する。
5. 差分全体のポリシー検査を行う。JS・PHP・複数ファイルなど、検査でLEVEL 2になった場合も、候補フォルダやパッチを書かず停止する。
6. 全検査を通った場合だけ、リポジトリ外に候補を作成してテストし、キューへ結果を返す。

停止時に残すのは依頼・分類の記録と結果です。候補・パッチ・テスト用修正版は作成しません。
「文字を黄色にして、太字機能も追加して」は依頼全体がLEVEL 2です。色変更だけを切り出しません。
「上のスペースをもっと有効活用して」のように完成状態が不明確なら、LEVELと別の追加確認フラグで止めます。
分類はモデルによる意味判断も使うため、曖昧な実メモを事前確認なしで流さないでください。

`--memo CM-<24桁の小文字16進ID>` を加えると、そのメモの処理待ちだけを取得します。`--once` との併用が必須です。
指定がない・保留中・既に終了・内容変更済みの場合、別メモへ切り替えません。同じ相談コードに複数の処理待ちがある場合も停止します。
別の処理が実行中なら取得しません。期限切れを含む別処理は管理画面で確認してください。
メモIDを指定しても自動送信・再送信はしません。管理者が内容を確認し、事前にキューへ送信する必要があります。
`--once` は取得なしや要確認の場合もその1回で終了し、2件目の取得をしません。

相談コード指定はサーバーの専用コマンド `claim_memo` を使います。**更新前のサーバーでは失敗して停止し、旧 `claim` へのフォールバックはしません。**
この機能を使う前に、変更した `codex_queue_lib.php` のレビュー・設置と、PC側ワーカーの更新が必要です。
今回の実装作業だけでは本番には反映されません。未コミット差分のあるリポジトリでは通常CLIは取得前に止まります。

configの `max_level` は `1` または `2` です。新しい設定例は `1`。既存設定で省略した場合は従来互換の `2`（LEVEL 2の候補・テスト後に要確認）です。
CLI指定とconfigのうち厳しい上限を採用します。`max_level: 1` を `--max-level 2` で緩めることはできません。
継続利用も `max_level: 1` と `--max-level 1` を使い、1件ずつ処理します。LEVEL 2・3や曖昧な依頼は候補作成前に要確認で停止します。
初回の1件試験成功後に開始してください。PC再起動時の自動起動設定は行いません。

継続利用のコマンド：
```powershell
python -B .deploy/codex_queue/worker.py --config C:/Users/idwor/Documents/Codex/timetable-queue/config.json --watch --max-level 1
```

`--watch` は15秒ごとにキューを確認し、1件ずつ処理します。既存の変更・接続不良などを検出すると停止します。
利用可能なCodexモデルはユーザーの既定設定を使い、必要な場合だけ設定の `model` で指定します。
PHPを変更する候補は構文確認まで行い、生成されたPHPをPCの権限で実行せず「要確認」にします。

## 保存場所・既存データの保護

- サーバー：新規 `data/codex_queue.php`。既存のロック・原子的保存・バックアップ機構を利用する。
- 元メモ：`data/codex_memos.php` を読み取るだけ。回答はキューを読み合わせて結果欄・コピー・ZIP出力へ追加する。元ファイルの移行や上書きはしない。
- PC：`workRoot/<処理ID>/` にメモ・添付画像・モデル応答・候補・パッチ・検査・受領記録を保存する。`request.json` へ処理トークンを保存しない。
- 候補：`candidate/`、`candidate.patch`、`manifest.json`。mainや本番ソースに直接書かない。
- 既存の `data/`、認証情報、アップロード、バックアップの転送除外は変更しない。Gitコミット中のプログラムだけをデータなしの候補フォルダに展開する。

`workRoot` には依頼の画像や本文があるため、GitHubや公開ディレクトリへコピーしないでください。保持期間と削除は管理者が別途管理します。
この機能は既存バックアップの削除や自動整理を行いません。

## 自動処理の制限

管理画面・APIは既存の管理者認証とCSRF対策を使います。教師・未ログイン利用者は操作できません。
ワーカー用操作はHTTPから404、SSHのPHP CLIからのみ受け付けます。ホスト・ユーザー・ポート・実行プログラムは固定し、確認済みホスト鍵との照合を必須にします。

サーバーはロックにより同時実行を1件に制限し、依頼の二重送信・内容変更・停止後の結果・期限切れを検出します。
PC側にも多重起動防止ロックがあります。結果の通信再試行は同一内容だけ受け付けます。

Codexは空の作業フォルダで読み取り専用、シェル・外部連携・ブラウザー・Web検索などを無効にして実行します。
選定したソースだけをテキストとして渡し、JSONの置換案を検査してからコントローラーが候補フォルダへ適用します。
危険なパス、認証・データ操作・外部通信・秘密情報のコード、削除、バイナリ、曖昧な置換を拒否します。
100ファイルの上限より厳しく、20ファイル・80置換・合計512KBで停止します。
JS・PHP・複数ファイルの変更は、モデルの判定にかかわらず最低LEVEL 2です。
危険変更の文字列検出とモデル判定には限界があるため、第1段階では検査成功でも本番反映しません。

## 検査と確認範囲

構文検査（PHP・JS・HTML内JS）、既存のデプロイ保護・復旧テスト、関連ページのHTTPと基本表示、
ログインページ・認証API・給与の未ログイン保護・非公開設定の非表示、候補のファイルハッシュ・元Gitの不変を確認します。
PHPが出力する `json_encode` 式はダミーのJS値に置き換えて構文確認し、PHP自体は別に `php -l` で調べます。他の動的テンプレートは無条件に省略しません。

HTTP・ブラウザー検査は本番と切り離した合成データを使います。未ログインでログインページへ移動する画面は、その保護までの確認です。
授業・出欠・給与などの業務操作がすべて正しいと保証するテストではありません。LEVEL 2の機能別回帰確認はレビュー時に追加します。

```powershell
$env:TIMETABLE_TEST_PHP = 'PHP実行ファイルの絶対パス'
python -B -m unittest discover -s .deploy/codex_queue -p 'test_*.py' -v
```

テストは一時フォルダの合成アカウント・メモだけを使用し、本番へアクセスしません。

## 停止と候補の確認

管理画面の「処理停止」または「保留」で対象を止めます。全体を止める場合は下記の `manage.py stop` を使います。実行中の1件の結果を返してから終了し、次の依頼は取得しません。直ちに止める場合はキュー画面で対象の「処理停止」を押してください。
強制終了後は次の接続で期限切れの依頼が「要確認」になります。再実行は別IDを発行し、前の記録を残します。
この停止操作は既存のGitHub Actionsの有効・無効を変更しません。

候補を取り込む際は `baseCommit` と現在のmainを照合し、`candidate.patch` とテスト結果をレビューします。
候補フォルダを本番へ丸ごとコピーしないでください。この段階には取り込みやGit書き込みの自動コマンドはありません。

## 次に自動pushを有効にする前に

1. この機能自体をレビューし、既存Actionsから導入してサーバーのPHP 7.4環境・権限・SSH接続で合成メモを確認する。
2. 実際の軽微な依頼でLEVEL判定・差分・機能別テスト・停止／再実行を複数回確認する。
3. 人間承認と一致する候補ハッシュ・base SHAだけを取り込む処理、mainが進んだ場合の再検証を追加する。
4. 独立した候補ブランチから相談コード付きのcommitを作り、LEVEL 1のみを許可する明示的な機能フラグと停止手段を追加する。
5. GitHubへ書き込む認証はOSの資格情報保管などで管理し、モデルから隔離する。現在のSSH資格情報やGitHub Secretsをコードへ移さない。
6. 対象SHAに一致する既存Actions Runを追跡し、デプロイとHTTP検査の成功後だけ「本番反映済み」にする。失敗・不明の場合は停止する。

第1段階を起動するための追加GitHub Secretsはありません。将来のpush有効化とは別です。

## このPCで普段使う方法

リポジトリ外の `C:/Users/idwor/Documents/Codex/timetable-queue/` にある「ワーカー開始.cmd」「ワーカー停止.cmd」「ワーカー状態.cmd」を使います。
開始は非表示のバックグラウンド処理です。PCが起動している間だけ動きます。多重起動はロックで拒否します。
停止操作は現在の1件を完了してから停止し、待機中なら通常15秒程度で終了します。
ソース変更や通信障害を検出した場合も停止します。勝手に再起動・再取得せず、ログを確認してから開始してください。

内部で使うコマンド（秘密値は引数に渡しません）：

```powershell
python -B .deploy/codex_queue/manage.py start --config C:/Users/idwor/Documents/Codex/timetable-queue/config.json
python -B .deploy/codex_queue/manage.py status --config C:/Users/idwor/Documents/Codex/timetable-queue/config.json
python -B .deploy/codex_queue/manage.py stop --config C:/Users/idwor/Documents/Codex/timetable-queue/config.json
```

「開始」は構成確認後に `enabled: true`、`max_level: 1` とし、通常CLIの `--watch --max-level 1` を起動します。
「停止」は `enabled: false` とします。他の設定や鍵は変更しません。処理ログは設定の `workRoot/worker.log` に保存します。
メモを記入して「Codexへ送信」を押すと取得され、候補と検査結果が元メモの結果欄に戻ります。
**候補の本番反映は自動では行いません。** 内容をレビューしてから別途依頼してください。
